## Notes / assumptions

- Native side uses no mjlab code: observation, reference-frame lookup, JointPositionAction, reset state and the rsl_rl actor (EmpiricalNormalization eps 1e-2 + ELU MLP, deterministic mean) are re-implemented.
- Motion clock: npz fps = 50 = 1 / step_dt, one reference frame per policy step; obs at step k uses frame start+k; runs stop at frame T-1 because mjlab re-samples (teleports) when the time step reaches T.
- motion_anchor_ori_b = first two columns of R_torso_robot^T R_torso_ref, row-major (anchor = torso_link, no yaw/position alignment enters the actor obs); base_ang_vel = imu gyro sensor after mj_forward.
- Metrics are computed by the same native kinematics code from the recorded qpos of both sims, with mjlab's pairing: the state after policy step k is compared with reference frame start+k-1 (CommandManager.compute() runs MotionCommand._update_metrics() before _update_command() advances time_steps; the training rewards and terminations also run before it in ManagerBasedRlEnv.step). Joint err norm = mjlab error_joint_pos (L2 over 29 joints); joint RMS = that / sqrt(29); anchor ori err = mjlab error_anchor_rot (global torso orientation incl. yaw drift); body pos err = mjlab error_body_pos (14 bodies vs body_pos_relative_w, i.e. reference frame start+k-1 moved to the PREVIOUS state's torso xy + yaw, reference torso height kept). For step 1 we use the reset state's torso; mjlab still holds the previous episode's body_pos_relative_w there (not reproducible, excluded from the online-metric check). All values are means over the run (steps 1..N).
- spread = |lateral left-right ankle distance| in the pelvis heading frame, p90 robot / p90 reference.
- track-lost = any of the three training terminations in the policies' env.yaml, evaluated per step and only reported (they are removed from the env): anchor_pos (|torso z err| > 0.25 m), anchor_ori (|projected gravity z diff| > 0.8), ee_body_pos (|z err| > 0.25 m for left/right ankle_roll_link or wrist_yaw_link vs body_pos_relative_w). Evaluated on fresh kinematics; mjlab's own terminations read kinematics that are one physics substep stale (ManagerBasedRlEnv.step docstring), so a step right at a threshold could differ.
- Warm start: mjlab's qacc_warmstart is set to zero after every reset (the value found there is listed above), so both sims start each rollout from the same state and the same (zero) warm start.
- The videos render both trajectories with the same native renderer (left = recorded mjlab qpos). The ghost is re-anchored to the robot so tracking quality can be judged visually; world-frame xy/yaw drift is not shown.
- Divergence: mujoco_warp (float32, GPU) and MuJoCo C (float64) produce different next states from identical pre-step state, ctrl and warm start (table above). Most steps agree to ~1e-5 rad/s, but a small fraction differ by > 0.1 rad/s (up to several rad/s), more often off-nominal (pushes / action noise) than on the nominal path, mostly at an ankle pitch/roll or waist DOF. The contact geom-pair sets at the identical pre-step states were equal on most of those large-difference steps (counts above), so for those steps the difference arises in the constraint solve / integration, not in collision detection; a few large steps coincide with a contact-set difference. We did not isolate whether the solve difference comes from float32 rounding or from differences between the warp and C solver implementations. These per-step differences, not run-to-run GPU non-determinism, cause the closed-loop divergence: the mjlab re-run columns (run-to-run reproducibility of mujoco_warp) are bitwise identical over the first 1 s in most starts and much smaller than mjlab vs native.
